# Accessibility screenshot capture

Updated 2026-10-24. **Latency is unmeasured.** This is API/source research, not a successful capture or performance result. First establish bounded emulator capture, teardown and failure behavior; only then collect separately authorized physical-device evidence. No sub-500 ms or sub-100 ms claim follows from API availability.

## API and capability

`AccessibilityService.takeScreenshot(displayId, executor, callback)` exists from API 30. Use `Display.DEFAULT_DISPLAY` for the default display. Declare `android:canTakeScreenshot="true"` in the service's accessibility metadata XML. Callbacks execute through the supplied executor. API 34 adds `takeScreenshotOfWindow`, which can avoid accessibility overlays covering the target window; full-display capture can include those overlays. [Android API reference](https://developer.android.com/reference/android/accessibilityservice/AccessibilityService#takeScreenshot(int,%20java.util.concurrent.Executor,%20android.accessibilityservice.AccessibilityService.TakeScreenshotCallback)).

The capability becomes `CAPABILITY_CAN_TAKE_SCREENSHOT` when Android parses the XML. It is absent from dynamically configurable service properties: `setServiceInfo` cannot supply a missing manifest capability. [AOSP AccessibilityServiceInfo](https://android.googlesource.com/platform/frameworks/base/+/refs/heads/main/core/java/android/accessibilityservice/AccessibilityServiceInfo.java#786).

**Existing enablement after updating metadata: unresolved on our devices.** AOSP tracks enabled services by component name, reparses metadata after package updates, and rebinds updated services. This suggests an ordinary same-package/component upgrade can retain enablement while refreshing the capability. It is an implementation inference, not a documented cross-version/OEM guarantee. Test an upgrade from the previous APK, inspect effective capabilities and service connection, and record whether a manual off/on is necessary. Do not silently change Settings or assume another user grant. [AOSP package-update handling](https://android.googlesource.com/platform/frameworks/base/+/refs/heads/main/services/accessibility/java/com/android/server/accessibility/AccessibilityManagerService.java#6550).

## Ownership, timing and failures

`ScreenshotResult` exposes a `HardwareBuffer`, color space and timestamp. The recipient must close the buffer. `getTimestamp()` uses `SystemClock.uptimeMillis()`, milliseconds since boot excluding deep sleep. Compare with the same device clock; wall time, host monotonic time and `elapsedRealtime()` are different domains. The API has no cancellation handle. AOSP dispatches through `executor.execute`; a timeout does not cancel the underlying capture. [AOSP client and ScreenshotResult](https://android.googlesource.com/platform/frameworks/base/+/refs/heads/main/core/java/android/accessibilityservice/AccessibilityService.java#2705).

AOSP currently rejects requests whose spacing is **≤333 ms**, updating the request timestamp before permission/display checks. This hidden implementation threshold is not a public scheduling guarantee; leave margin and handle `ERROR_TAKE_SCREENSHOT_INTERVAL_TIME_SHORT`. Missing capability can throw `SecurityException` synchronously. Other paths return callback errors, including absent access and invalid display. The success timestamp is populated in a posted delivery runnable after capture, so it does **not** establish original presentation time or true pixel age. [AOSP server capture path](https://android.googlesource.com/platform/frameworks/base/+/refs/heads/main/services/accessibility/java/com/android/server/accessibility/AbstractAccessibilityServiceConnection.java#1467), [333 ms constant](https://android.googlesource.com/platform/frameworks/base/+/refs/heads/main/core/java/android/accessibilityservice/AccessibilityService.java#788).

`ERROR_TAKE_SCREENSHOT_SECURE_WINDOW` and invalid-window errors were added in API 34. Do not assume the API 30 full-display path returns these window-specific errors. `FLAG_SECURE` prohibits screenshot inclusion of protected content; inaccessible pixels are not a capture optimization opportunity. [Error reference](https://developer.android.com/reference/android/accessibilityservice/AccessibilityService#ERROR_TAKE_SCREENSHOT_SECURE_WINDOW), [FLAG_SECURE](https://developer.android.com/reference/android/view/WindowManager.LayoutParams#FLAG_SECURE).

## Bitmap and encoding

`Bitmap.wrapHardwareBuffer(buffer, colorSpace)` can return null or throw for invalid arguments. A successfully wrapped bitmap retains its own buffer reference, so the original `HardwareBuffer` may then close. Do not modify the backing buffer while used. `Bitmap.copy(ARGB_8888, false)` can produce an independently owned software bitmap, but can return null. Scaling requires positive dimensions and can return the original bitmap when unchanged; avoid double recycling aliases. `compress` returns success/failure and belongs on a worker thread. [Bitmap contracts](https://developer.android.com/reference/android/graphics/Bitmap).

JPEG quality controls visual fidelity and drops alpha; PNG is lossless and ignores quality. Explicit WebP lossy/lossless formats are available at API 30; lossless quality controls compression effort rather than fidelity. Scaling and encoding cost must be measured independently; smaller output bytes do not prove faster acquisition. [Compression formats](https://developer.android.com/reference/android/graphics/Bitmap.CompressFormat), [AOSP encoder definitions](https://android.googlesource.com/platform/frameworks/base/+/refs/heads/main/graphics/java/android/graphics/Bitmap.java#1492).

## Experiment requirements inferred from these contracts

Use one in-flight request and a bounded worker executor; never block the callback's own executor awaiting its completion. Keep late callback cleanup alive after timeout/Stop, close every returned buffer even when its result is obsolete, and fence delivery by session generation. Executor rejection or discarded queued callbacks can strand resources. Catch synchronous exceptions as well as callback failures. Record request→callback, bitmap conversion, scaling, compression, transport, total return, and API timestamp age separately. A monotonic visible counter or controlled response is needed to substantiate freshness. These are engineering recommendations, not platform latency guarantees.
